Methodology

1. Composio catalog check (first-party)

composio.toolkits.get(slug=...) checks Composio's own toolkit catalog for each app before any research — if a toolkit already exists, that's authoritative proof of buildability straight from the platform, not an inference.

2. Direct fetch, LLM extracts (provider-flexible)

Each app's known docs URL is fetched directly (no API key needed) and given to whichever LLM key is present — Groq, Anthropic, or OpenRouter — to extract fields, with search used only as a fallback when the direct fetch fails. Schema and evidence validation retries failures with backoff.

3. Verification sample

A reproducible random sample (fixed seed) is re-checked field-by-field against its own cited source, logged CORRECT / INCORRECT / UNVERIFIABLE with a full audit trail.

4. Human correction

Confirmed errors are corrected and flagged human_corrected before being counted in the patterns below — the reported accuracy is post-correction, not the agent's raw first pass.

5. Pattern analysis

Computed directly from the corrected dataset — category-level claims only render when enough apps in a category have been researched to support them.

Limitations

  • APIs and auth requirements change — every record carries a researched_at timestamp.
  • OAuth/approval requirements can vary by account tier even within one app.
  • "Buildable" means publicly documented access existed at research time, not a guarantee Composio has built the toolkit — though the catalog check shows where one already exists.
  • Verification re-checks the sources an app was researched from, not the full space of possible sources.
  • Category-level comparisons only render once enough apps per category are researched to be meaningful — see coverage banner above.
